# 测试

本文按源码包与被测对象组织。当前共有 **264 条 JVM 用例**（`app/src/test` 259 条，`app/src/testDebug` 5 条）和 **79 条 instrumented 用例**（`app/src/androidTest`），合计 343 条。

## 一、测试基线

1. JVM 用例使用 JUnit4（`org.junit.Assert`）与 `runTest`；Room 相关用例使用 Robolectric（`@Config(sdk = [35], application = Application::class)`）和内存数据库。
2. Instrumented 用例使用 `AndroidJUnit4`、设备上的真实 SQLite 与 `runBlocking`；Compose 用例使用 `createComposeRule` 或 `createAndroidComposeRule`；Hilt 端到端用例依赖 `HiltTestRunner` 与 `TestDatabaseModule`。
3. 时间基线为 `2026-10`（`[2026-10-01, 2026-11-01)`）、`today = 2026-10-20`、时区 `Asia/Shanghai`；日期均按半开区间处理。Compose 用例的 `today` 由 `EnvelopeUiState.Success.today` 注入（例如 `EnvelopeScreenInstrumentedTest` 传入 `2026-11-05` 构造“过去月份”），端到端导航用例改用注入的 `Clock` 与设备当前月份。
4. 金额单位为“分”，金额断言均为 `Long` 精确值。
5. Room 相关 JVM 用例的数据由 `testing/RoomTestData` 构造：信封 A、B，预算 D1~D3，支出 B1~B8，未知信封（或未知预算）使用 `envelopeId(0xEE)` 一类工厂生成。`EnvelopeViewModelTest`、`OverviewViewModelTest`、`BudgetCalendarModelTest`、`QuickSetBudgetPlannerTest`、`EnvelopeUiStateTest` 只复用其中的 `envelopeA`/`month`/`uuid` 等常量，数据在各自用例内构造。
6. Instrumented 数据由 `testing/InstrumentedTestData` 构造；Hilt 端到端用例使用 `TestDatabaseModule` 的内存数据库。
7. 执行方式：JVM 全量使用 `:app:testDebugUnitTest`（同时包含 `test` 与 `testDebug`）；instrumented 使用 `:app:connectedDebugAndroidTest`，需要真机或模拟器，当前共 79 条。

| `isDeletable_falseWhenALiveExpenditureAllocatesToTheEnvelope` | 存活支出 `0xB1`（`10-05`）分摊 A 6000：返回 `false`；同时核对汇总行 `canDelete == false` |

`isDeletable(id)` 的判定条件是「不存在 `deletedAt` 为空的预算」且「不存在指向未软删除支出的分摊」：软删除的预算与支出不挡住删除，因此该判断与 `budget`、`expenditureAllocation` 对 `envelope` 的 RESTRICT 外键的实际拒绝时机一致（真实 SQLite 上的对应用例见 15.1）。查询不检查信封行本身是否存在，未知信封一律返回 `true`，是否存在由 `delete` 的返回行数区分。

`observeSummaries` 的 `canDelete` 列把同一条判定按行内关联子查询实现（`EXISTS` 只匹配 `envelopeId = ev.id`，不看归属月份或日期窗口），因此它与 `isDeletable(id)` 口径一致，上述 `isDeletable_*` 用例把两者放在同一份数据上交叉验证；列值为 `false` 只表示删除会被外键拒绝，不代表信封行本身有问题。

`currentSpanAllocated` 的统计窗口：today 落在某个未删除预算的 `[startDate, endDate)` 内时，统计该区间内的全部分摊（保持原行为）；today 不在任何预算区间内（包括没有预算）时，只统计 `happenedDate == today` 的分摊。回退逻辑只作用于 `isBudgeted = true` 的信封。

说明：`observeSummaries` 会返回归档信封行，以便汇总总支出；界面层由 `OverviewViewModel` 过滤归档信封并排除其预算。

## 附：覆盖边界

1. 归档信封：`EnvelopeDao.observeSummaries` 仍返回归档行，以保留“归档交易计入总支出”的能力；`OverviewViewModel` 负责从列表隐藏归档信封，并在汇总预算中排除归档预算。对应用例为 `OverviewViewModelTest` 的两条。
2. 软删除：预算查询、信封汇总、分摊明细与按日汇总均排除 `deletedAt` 非空的行；对应用例分布在 `BudgetDaoTest`、`EnvelopeDaoTest`、`ExpenditureAllocationDaoTest` 及 instrumented 的 `EnvelopeSummaryQueryInstrumentedTest`。软删除行的物理清理由 `BudgetDao.clean`、`ExpenditureAllocationDao.clean`、`ExpenditureDao.clean` 完成，用例在 `BudgetDaoTest`、`ExpenditureAllocationDaoTest`、`ExpenditureDaoTest` 与 `RoomEnvelogRepositoryWriteTest`，并在真实 SQLite 上由 `EnvelopeDeleteInstrumentedTest` 复验。
3. 预算区间：`List<HalfOpenDateSpan>.hasOverlap()`、`BudgetDao.countOverlaps` 与 `insertEnvelope`/`insertBudget`/`updateBudget`/`replaceBudgets` 的 `BudgetWriteResult` 共同覆盖重叠拒绝；相邻区间不算重叠。
4. `ExpenditureSubmission` 不再接收手写的 `happenedDate`，由 `happenedAt` 和 `happenedZone` 推导；相关断言在 `MappersTest` 与 `RoomEnvelogRepositoryTest` 中。
5. 未覆盖：预算按权重分配、日期选择器交互。`RecordViewModel` 仍无独立测试类。
6. `EnvelopeCalendarModel.of` 的 `budgets = null` 分支（非预算型信封）没有直接用例，只由 `EnvelopeUiStateTest` 经 `EnvelopeUiState.Success` 间接覆盖。
7. 信封删除：JVM 用例覆盖 `deleteEnvelope` 的四种返回与事务回滚，以及 `canDeleteEnvelope` 与删除结果的一致判断；`ExpenditureDao.clean` 早于 `ExpenditureAllocationDao.clean` 的顺序约束由 `RoomEnvelogRepository` 保证，反序后果记录在 `clean_findsNoCandidateAfterAllocationsWereCleanedFirst`。真实 SQLite 上的删除与级联由 `EnvelopeDeleteInstrumentedTest`（14 条）与 `RoomEnvelogRepositoryInstrumentedTest` 的 4 条 `deleteEnvelope`、4 条 `canDeleteEnvelope` 用例覆盖：RESTRICT 拒绝、CASCADE 级联、软删除主键释放，以及 `isDeletable` 的放行与实际约束拒绝是否一致均已验证。`observeSummaries` 的 `canDelete` 列只由同一份数据与 `isDeletable` 交叉比对（6.1 的 9 条 `isDeletable_*`、15.1 的 4 条），没有独立的列级用例，因此列值的覆盖范围与判断方法一致，不含「引用行属于其他归属月份或日期窗口」之外的额外分支。仍未覆盖的是 `deleteEnvelope` 只清理垃圾行这一功能边界——存在存活预算或存活分摊的信封一律返回 `Contraint`；判断方法目前只到查询结果与仓库层；界面层入口已建立（信封编辑页底部按钮、总览管理态卡片图标，均在 `canDelete` 为真时走删除，否则走归档），确认对话框用例见 15.6，`canDelete` 的写入后失效与删除预算后重查见 11.2；`EnvelopeViewModel.deleteAndBack()` 与 `EnvelopeScreen` 的删除按钮、`OverviewViewModel.deleteEnvelope` 本身仍无用例。
